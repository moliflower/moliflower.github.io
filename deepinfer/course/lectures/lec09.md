# 第 9 讲：从单请求分页到共享块池

先修：[第 7 讲](lec07.md)、[Lab3](../labs/lab03/README.md)、[HW2](../hw/hw02/README.md)。本讲约 45–60 分钟，加 Lab4 约 2–3 小时。无需 GPU。

学完应能回答：多条请求怎样使用同一个有限块池？一个请求结束时，为什么不能把它引用的所有块直接清零？

## 1. Lab3 还没有解决什么

Lab3 的 PagedKVCache 为一条序列不断创建字典项，说明了逻辑页到物理页的映射；它没有设备容量上限，也没有多个请求共享块的生命周期。现在增加一个限制：物理池只有 3 块，每块可存 4 个 token。

A 的长度为 5，需要 2 块；B 的长度为 4，需要 1 块。两者正好占满。C 再来时必须等待、回收或采用其他策略，不能凭空分配第 4 块。本周只实现拒绝分配与等待；抢占和换出不是默认行为。

## 2. 地址转换分两步

设块大小为 B、逻辑 token 位置为 t：

```text
logical_block = t // B
offset = t % B
physical_block = block_table[logical_block]
```

用 `table=[9,2,7]`、B=4 手算：

| t | 逻辑块 | 物理块 | 块内偏移 |
| :--- | :--- | :--- | :--- |
| 0 | 0 | 9 | 0 |
| 3 | 0 | 9 | 3 |
| 4 | 1 | 2 | 0 |
| 11 | 2 | 7 | 3 |

物理块编号不用连续。这里的 `(physical_block, offset)` 还不是设备 byte 地址；真实布局还需层、K/V、head 和元素大小等信息。`locate` 只检查已分配槽位，不知道序列真实长度，所以请求层还必须检查 `t < sequence_length`。

## 3. 先证明可以成功，再改变状态

块池用 `refs=[0,0,0]` 表示三个空闲块。申请 2 块之后得到 `[0,1]`，refs 为 `[1,1,0]`。接着申请 2 块应抛 MemoryError，refs 必须仍为 `[1,1,0]`。

错误写法是一边扫描一边标记：先占用块 2，再发现缺块，抛异常。调用者没有收到可释放的块 ID，池却泄漏了一块。

正确的操作分成两段：检查并收集候选；确认数量足够后统一修改。这里的“原子”只指单线程函数在失败时不留下部分修改，不代表实现了并发锁。

## 4. 引用数表示还有多少所有者

假设 A 拥有 `[0,1]`，B 复用完整前缀块 0，同时拥有自己的尾块 2：

| 操作 | refs | 空闲块数 |
| :--- | :--- | :--- |
| A 申请两块 | `[1,1,0]` | 1 |
| B retain 块 0，并申请块 2 | `[2,1,1]` | 0 |
| A 结束，release `[0,1]` | `[1,0,1]` | 1 |
| B 结束，release `[0,2]` | `[0,0,0]` | 3 |

对每一块维护不变式：`refs[block] == 仍引用该块的所有者数量`。只有 refs=0 才可重新分配。Lab4 不存 KV 数值，也不缓存已结束请求；第 10 讲会区分“无人引用”与“仍有可复用内容”。

本课仅共享已经写满且不再修改的前缀块。若两个请求共享未写满的尾块后各自追加不同 token，就必须先复制或采用其他隔离机制。不能只加引用数再同时写同一块。

## 6. 对照真实系统

PagedAttention 将 KV 按块管理，通过块表访问非连续存储，并支持共享。以上练习只模拟块生命周期，不实现 attention kernel。阅读 [PagedAttention 原论文](https://arxiv.org/abs/2309.06180) 的内存管理部分，再在仓库 `csrc/engine/block_manager.hpp` 中寻找分配与回收的边界。只记录一个与自己的模型相同的约束和一个未模拟的机制。
