第 10 讲：前缀命中、共享与淘汰

1. 命中的是上下文，不是单独一块的文字

考虑 token 序列 [1,2,3,4,5,6] 和 [9,2,3,4,5,6]。虽然后面五个 token 相同，但因更早的上下文不同，不能假定它们的 KV 相同。

本课使用固定模型、固定推理配置、确定性 token 输入的教学假设，只复用从位置 0 开始完全相同的前缀。实际服务还需要隔离模型版本、适配器、多模态输入等影响计算的条件。

vLLM 的前缀缓存设计用父块的标识、当前块 token 和附加条件识别内容；不能仅以当前块文字作为键。见 vLLM 前缀缓存设计（核对日期：2026-10-23）。本课用完整 token 比较避免引入哈希碰撞问题。

2. 完整块规则

缓存序列为 [1,2,3,4,5,6,7]，查询为 [1,2,3,4,5,9]。最长公共前缀为 5。B=4 时只复用前 4 个 token：

hit_tokens = (common_prefix_length // B) * B

不要向上取整，否则会把并不相同的第 6–8 个 token 算入命中；也不要继续搜索第一个差异之后的相同子串。请求短于缓存时，命中长度不能超过请求长度。

这里只统计可复用 KV 的 token 数。它不保证可以跳过模型所有计算，也不直接等于 TTFT 加速比例。输出 logits、调度与运行时实现不在该指标内。

3. 共享前缀后的容量推导

三条请求长度为 [5,8,9]，B=4，全部共享长度为 4 的完整前缀。

不共享时，每条独立向上取整，占 8+8+12=28 个槽位。共享时：前缀只保留 4 个槽位，三个私有后缀长度分别为 1、4、5，分别占 4、4、8 个槽位，共 4+4+4+8=20。

shared_slots = prefix_tokens
             + sum(ceil((length-prefix_tokens)/B)*B)

约束：前缀长度是 B 的倍数且不超过任一请求长度。没有请求时不保留前缀，返回 0。此公式与 HW2 的 prefix_cache_savings 口径不同：HW2 已有一份额外保留的前缀，此处在当前请求集合内部共享一份。回答容量题前先明确“原来有几份、现在有几份”。

4. 无人引用不等于内容必须立即擦除

Lab4 中 refs=0 意味着可重新分配；如果保留该块的旧内容和索引，它也可以暂时作为缓存。新请求命中后再次取得引用；需要腾出空间时才淘汰。这里区分可覆盖的物理空间和仍可利用的历史数据。

HW5 的简化策略：先筛选 refs=0 的块，再按 last_used 从小到大淘汰；同时间按物理 ID 升序。refs>0 的块即使最旧也不能淘汰。

例：refs=[1,0,0,0]、last_used=[0,9,3,3]，候选顺序为 [2,3,1]。最旧的块 0 仍在使用，必须保留。真实系统可能有层级、分组和其他策略；不要把本题的排序当成所有引擎的固定实现。

5. 三个容易误报的结论

  • “命中率 80%”需要说明分母是请求、token 还是块。相同的请求命中率可能对应很不同的节省量。
  • “节省 8 个槽位”是容量结论，没有测量就不能说快了多少。
  • “refs=0”只表示没有活动所有者，不代表没有缓存元数据需要清理。

完成 HW5 后，在 Project2 Phase1 观察一个慢的大请求怎样阻塞队列。本阶段不实现前缀缓存接入，先把所有权、容量和等待行为做成可验证的事件记录。
